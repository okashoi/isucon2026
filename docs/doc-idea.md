### この問題の構造（施策の前提）

- **スコアの主役は「投稿 → 友達のフィードで検証通過」(10/20点)と「エクスポート」(20点)**。閲覧系はユーザー×投稿期間ごとに上限があるため、スコアを伸ばす＝**投稿期間のサイクルを速く・多く回し、ユーザー数（特に europe/america の1.5倍）をさばき切る**こと。
- **europe1 / america1 は共有DB (asia2) まで WAN 越し**（遅延＋帯域制限、しかもルーター経由）。1リクエストあたりの DB 往復回数とデータ転送量が、1.5倍リージョンのレイテンシ・スループットを直接決める。**「クエリ数を減らす」「画像バイト列を国内に置く」が本質**。
- 猶予はほぼゼロ（削除画像の5秒のみ）なので、TTL キャッシュは原則使えない。使えるのは**不変データのキャッシュ**と**イベント purge 型キャッシュ**。

## 3. 施策アイデア（優先度順）

### 施策1: 画像配信パイプラインの再構築【効果: 大 / 序盤〜中盤】

- 根拠: 「画像の取得 2」「過去の投稿の画像の取得 2」×ユーザーあたり4回/期間＋投稿直後の確認（上限外）。「リージョン間の通信には遅延と帯域制限があります」。スキーマコメント「画像をDBにおかないと、別のサーバーからデータを返却したときに404になってしまう」。
- 現状の問題:
  - `GET /api/images/:imageId` は毎回 asia2 から **bytea を WAN 越しに転送**（[go/image_api.go:70](../go/image_api.go#L70)）。
  - image_objects は月別パーティションで PK が `(id, created_at)`（[sql/001-schema.sql:30](../sql/001-schema.sql#L30)）。id 単独の検索は**全パーティション（約40個）を当たる**。
  - 署名検証・生成が **HMAC-SHA256 ×1000回反復**（[go/image_signature.go:15](../go/image_signature.go#L15)）。フィード1ページ＝投稿50件×（投稿画像＋著者プロフィール画像）で最大100回 `signedImageURL` が呼ばれ、1リクエストで数十msの純CPU。
- 施策:
  1. **画像バイト列の各アプリサーバでのキャッシュ**（メモリLRU＋ローカルディスク）。画像の中身は不変なので purge 不要。配信可否（投稿削除・退会・RealMoji差し替え）だけ DB に軽いクエリで確認する。削除チェックは [go/image_api.go:65](../go/image_api.go#L65) のコメント「削除状態を毎回確認する。即時反映も5秒以内の許容範囲に含まれる」のとおり投稿削除には5秒猶予があるが、RealMoji 等への適用は不明（要確認 #1）なので、可否チェック自体は毎回 DB で行い、**bytea を運ばない**ことに価値を置く。
  2. **署名計算のメモ化**。`(imageID, exp)` → sig をキャッシュ。exp を「次の分境界＋24h」のように切り上げでバケット化すればヒット率が上がる（URL 形式・24h以上の有効期限は維持。丸めの可否は要確認 #3。保守的には秒単位メモ化でも同時アクセス分は効く）。検証側（[go/image_api.go:60](../go/image_api.go#L60)）も `(imageID, exp) → 正しいsig` を引けば再計算不要。
  3. **image_objects を通常テーブル化**（パーティション廃止、`id` PK）。スキーマ変更は明示的に許可されている。変更時は [sql/reset.sql](../sql/reset.sql) のパーティション TRUNCATE 処理と初期スナップショットの整合を取り、「初期データの履歴と画像も取得できる状態」を維持する。
  4. 可否チェッククエリの単純化: 既に部分インデックス `posts_image_id_author_id` / `realmojis_image_id_reactor_id` がある（[sql/reset.sql:47-49](../sql/reset.sql#L47)）ので、bytea を含む行の取得と分離する。
- 過去事例: reference 観点9（アイコン配信の Cache-Control / 304、[13] icon_hash の事前計算）、観点15（[7q] 帯域制限下で転送量削減）。
- リスク: 「署名と期限の形式や検証結果を変えてはいけません」→ **反復回数1000は変えない**（ベンチマーカーが自前で署名を計算して突き合わせる可能性が高い。abuse 検知 `invalid_signature` の存在がその傍証）。キャッシュは `/api/initialize` で必ず破棄（「独自に追加したキャッシュや複製先も初期化してください」）。

### 施策2: リクエストあたり DB 往復数の削減（セッション・viewerContext）【効果: 大 / 序盤】

- 根拠: 「サーバ間の通信はルーターを経由します」「リージョン間の通信には遅延と帯域制限があります」＋ europe/america は配点1.5倍。往復1回のコストが asia の数十倍になり得る。
- 現状の問題（フィード1回で最大9クエリ＝9往復）:
  - 全認証リクエストでセッションを DB 照合（[go/session.go:50](../go/session.go#L50)）。しかも **login_sessions.token_hash にインデックスがない**（全件スキャン）。
  - `loadViewerContext`（[go/post.go:103](../go/post.go#L103)）が getUser / HasPostedToday / blocked / friends / 友達の友達 で **5クエリ**。feed・投稿詳細・コメント・RealMoji・権限判定のたびに呼ばれる。
- 施策:
  1. **インデックス追加（最優先・ノーリスク）**: `login_sessions(token_hash) WHERE active`、`users(username)`、`notifications(user_id, created_at)`、`block_relations(blocked_id)`、`follows(followee_id)`、`friend_requests(recipient_id, status)` / `(requester_id, status)`。追加は [sql/reset.sql:47](../sql/reset.sql#L47) の CREATE INDEX 群に載せると initialize 後も維持される。
  2. **セッションのアプリ内キャッシュ**: token_hash → (user_id, region)。login/logout/退会/再ログイン時に purge。ユーザーの書き込みは原則本人のリージョンのサーバに来る（[go/region.go](../go/region.go)）ためサーバローカル purge で足りるが、`POST /api/auth/logout`・`PATCH /api/me` には RegionMiddleware がない（[go/server.go:50-56](../go/server.go#L50)）点だけ検証する。
  3. **viewerContext の1〜2クエリ化**: friends＋friends-of-friends＋blocked＋HasPostedToday を CTE でまとめ、1往復で取る。さらに進めるなら友達グラフ（friendships / blocks / follows は小さく画像を含まない）を**全サーバでオンメモリ化し、更新 API で書き込み後に他サーバへ purge を同報**（ルーター経由の HTTP で可。即時反映要件があるため「書き込みレスポンスを返す前に」purge を完了させる）。
- 過去事例: reference 観点4（[5q] users/relations 全件オンメモリ）、観点15（JOIN のない小テーブルの分離・キャッシュ）。
- リスク: 「書き込みが成功した後の読み取りには、その結果を反映します。リージョンをまたぐ場合も同じです」→ TTL は不可、purge 型のみ。クロスリージョン purge の往復（1 WAN RTT）は書き込み系（2点以下）に載るので、読み取り系（フィード10/20点の検証経路）を軽くする取引として成立する。

### 施策3: フィードクエリの SQL 化と LIMIT【効果: 大 / 序盤〜中盤】

- 根拠: 「投稿後の友達フィードの検証通過 10／最後の投稿期間 20」「フィードの閲覧 1」×20回/ユーザー/期間。スコアの本丸である友達フィードの速度と正しさが最重要。
- 現状の問題: [go/feed_api.go:72](../go/feed_api.go#L72) が**アクティブな投稿期間の全投稿を全件取得**（LIMIT なし、著者 JOIN 込み）→ Go 側で可視性フィルタ（[go/feed_api.go:80-85](../go/feed_api.go#L80)）。ユーザー数×投稿で肥大し、WAN 転送量も比例増。ranked フィード（friends-of-friends）はページングでも毎回全件再取得（[go/feed_api.go:69-71](../go/feed_api.go#L69)）。
- 施策:
  1. friends / following / public フィードは可視性条件（友達 ID リスト・visibility・ブロック）を SQL に押し込み `LIMIT 51`。`posts(posted_at DESC, id DESC)` 複合インデックスを追加。
  2. friends-of-friends（ranked）はスコア計算（[go/feed_api.go:128](../go/feed_api.go#L128)）が重いので、候補の絞り込み（友達の友達の author のみ）を SQL 化した上で、ページング用にスコア付き結果を**ユーザー単位で短命キャッシュ**（同一ユーザーの連続ページングは同一スナップショットで良いかは要確認 #4。保守的にはキャッシュせず都度計算でも、候補絞り込みだけで大幅に減る）。
  3. 投稿→フィード反映の検証（10/20点）が最優先なので、friends フィードを最速にする。
- 過去事例: reference 観点5（配点表で導線に優先順位）、[11f] OFFSET→seek 方式。
- リスク: クリティカルエラー②③「フィードに存在しない投稿や閲覧権限のない投稿が返されること」。可視性ロジックの SQL 移植は characterization テスト（AGENTS.md の方針どおり）を先に書いてから。

### 施策4: 通知 SSE のポーリング排除（LISTEN/NOTIFY）【効果: 中 / 中盤】

- 根拠: 「通知の受信 1」「投稿期間の開始時には、対象リージョンの利用者に通知を作成します」。通知はシナリオの起点（通知→投稿→フィード閲覧）なので、遅いと期間サイクル全体が遅れる。
- 現状の問題: SSE 接続ごとに **500ms 間隔で getUser＋通知クエリの2往復**（[go/notification_api.go:37-56](../go/notification_api.go#L37)）。接続数×4クエリ/秒が常時 DB（WAN 越し）に流れる。notifications(user_id, created_at) のインデックスもない。
- 施策: PostgreSQL の LISTEN/NOTIFY（または投稿期間開始の同報）で各アプリサーバのメモリに「リージョンの最新 window」を持ち、SSE は接続時に1回 DB を引いた後はメモリ上のイベント待ちにする。通知レコード自体は現行どおり INSERT（レスポンスの id 等に使うため）。
- 過去事例: reference 観点1（[14] 通知のポーリング間隔調整・ロングポーリング）、観点12（シナリオの律速）。
- リスク: 通知は「作成時刻が接続後」のものだけ返す現実装の挙動を変えない。region 変更・退会ユーザーの切断条件（[go/notification_api.go:47](../go/notification_api.go#L47)）も維持。

### 施策5: 書き込み系のロック競合解消【効果: 中〜大 / 中盤】

- 根拠: 投稿（フィード検証10/20点の起点）、RealMoji 5点、コメント3点は全て書き込み。地域内の全投稿が直列化されるとスコアの天井になる。
- 現状の問題:
  - `POST /api/posts` が**アクティブな posting_window 行を FOR UPDATE**（[go/post_api.go:107](../go/post_api.go#L107)）→ リージョン内の全投稿が直列化。しかも同一トランザクションで bytea INSERT と jpeg.Decode 済みデータの書き込みを抱える。
  - `POST /api/auth/register` と投稿期間の開始が **`LOCK TABLE users IN SHARE ROW EXCLUSIVE MODE`**（[go/user_api.go:93](../go/user_api.go#L93), [go/admin_posting_window_api.go:46](../go/admin_posting_window_api.go#L46)）→ 登録同士が直列化し、さらに users への全 UPDATE（プロフィール変更・退会・認定）をブロック。
  - 社交系 API は毎回両ユーザー行をロック（[go/relationship.go:37](../go/relationship.go#L37)）。
- 施策:
  1. register: `users(username)` にユニークインデックスを張り、LOCK TABLE を撤去して INSERT の一意制約違反を 409 に変換。
  2. createPost: window の FOR UPDATE をやめ、「1期間1投稿・削除2回まで」を posts への部分ユニークインデックス（local_date を posts に非正規化）＋条件付き INSERT で担保。window 終了との競合窓は投稿期間の切替時のみで、クリティカルエラーの定義（権限・削除画像）には触れない。
  3. 投稿期間開始の LOCK TABLE は頻度が低い（リージョンごとに期間切替時のみ）ので当面維持し、通知 INSERT の対象を `users_region_status` インデックス（既設）で速くする。
- 過去事例: reference 観点6（[9q] critical 対象だけ mutex、他はロックを緩める）、[8q] 講評「デッドロックが低確率で発生するが高速な実装も選択できる」相当の割り切り（ただし本回はエラー減点なし・FAIL 条件のみなので、クリティカルエラー6種に触れない範囲で攻められる）。
- リスク: 二重投稿が「フィード検証」の期待値を壊す可能性。ユニーク制約で DB レベルの保証を先に入れてからロックを外す順序で。

### 施策6: ユーザー検索の前計算【効果: 中 / 中盤】

- 根拠: 「ユーザーの検索 2」。友達申請（2点）の導線でもある。
- 現状の問題: [go/user_read_api.go:45](../go/user_read_api.go#L45) が**全ユーザーを毎回取得**し、1行ごとに NFC 正規化＋ケースフォールド（[go/user_read_api.go:55](../go/user_read_api.go#L55)）。ユーザー数に比例して悪化し、登録が進むほど重くなる。
- 施策: username / display_name の正規化済みカラムを追加（登録・プロフィール変更時に Go 側で計算して保存）し、`LIKE '%q%'` ＋ pg_trgm GIN インデックスで検索。ORDER BY username, id のページングは `users_status_username_id`（既設）が効く。
- 過去事例: reference 観点4（変更タイミングが限られる値の前計算）。
- リスク: 正規化関数（`cases.Fold()`＋NFC）と完全に同じ結果になることをテストで担保。部分一致の意味は変えない。

### 施策7: エクスポートのストリーミング化と Memories の整備【効果: 中 / 中盤】

- 根拠: 「エクスポート 20」「Memoriesを月単位で閲覧 3」「Memoriesやエクスポートなどの確認は…一連の確認に成功した回数」。1回20点は単価最大。クリティカルエラー⑤「初期データの期待値と一致しないこと」の対象でもある。
- 現状の問題: [go/export_api.go:30](../go/export_api.go#L30) が全投稿の bytea を1クエリで取得し、**zip 全体をメモリ上に構築**。初期データの投稿が多いユーザーでメモリスパイクと WAN 転送集中。
- 施策: zip をレスポンスライターへ直接ストリーム（Store のままなので CPU 負荷なし）。画像はバッチ分割して取得。施策1の画像キャッシュが入れば初期データ分はローカルから出せる。
- 過去事例: reference 観点7（[8q] レポートのストリーミング出力、Swap 対策）。
- リスク: posts.json の構造・画像パス（`images/%06d.jpg`）・順序（posted_at, id 昇順）を変えない。

### 施策8: abuse IP の BAN（初期実装の調整弁を使う）【効果: 中 / 負荷が上がってから】

- 根拠: 初期実装に ip_bans テーブル＋`IPBanMiddleware`（403）＋200ms リロード（[go/ip_ban.go:14](../go/ip_ban.go#L14)）、`invalid_signature`（署名偽造。期限切れとは区別されている）と `invalid_image` の abuse ログ（[go/image_api.go:61](../go/image_api.go#L61), [go/profile_image_api.go:26](../go/profile_image_api.go#L26)）。「ベンチマーカーは、このヘッダー（X-Client-IP）を使ってユーザーごとに異なるIPアドレスを指定します」→ IP 単位の遮断が設計上可能。
- 施策: abuse を記録した IP を ip_bans に INSERT（banned_until 付き）。偽造署名の検証は 1000 回 HMAC＋DB 2クエリを食うため、BAN で入口（ミドルウェア）で落とすと CPU/DB が浮く。
- 過去事例: reference 観点10（[10q] bot 503、[8f] ブルートフォース BAN、[12q] BAN ユーザーの高速拒否）。
- リスク: **マニュアルに BAN の明示的許可はない**。誤 BAN は正当ユーザーの全 API を 403 にし、フィード検証失敗（＝加点機会喪失）や「閲覧権限のない〜」系の誤判定を招く。先に abuse ログを info レベルで観測し、アタッカーの挙動（同一 IP から反復するか）を確認してから、ポータルで質問（要確認 #2）するか小さく試す。

### 施策9: ミドルウェア・設定のチューニング【効果: 中 / 序盤】

- ログ: `ISUREAL_LOG_LEVEL` 既定 error（[go/config.go:39](../go/config.go#L39)）で 5xx だけを JSON ログ出力する。攻撃の検知は `AbuseBanMiddleware` が行うのでログに依存しない。通信を調べるときは `debug` にする。
- DB 接続: `SetMaxOpenConns(30)`（[go/server.go:34](../go/server.go#L34)）。WAN 越しのクエリは接続を長く占有するため、PostgreSQL の max_connections と合わせて引き上げる（3アプリサーバ合計で считать）。
- PostgreSQL (asia2): shared_buffers / wal_buffers / checkpoint 設定、`synchronous_commit = off` は定番だが、追試の「再起動後にデータが取得できるか」は正常再起動なので WAL フラッシュされる。OS クラッシュ時のみリスク。導入するなら終盤ではなく早めに入れて安定性を見る。
- nginx: keepalive、`/assets` の静的配信（内容は変更不可だが配信方法は自由）、client_max_body_size（画像アップロードは最大 4096×4096 JPEG）。
- 過去事例: reference 観点7・9（定番のミドルウェア整備）。

### 施策10: 台数構成の見直し【効果: 大 / 中盤以降の伸びしろ】

- 根拠: 「初期状態で全てのサーバを使用します」「asia1とasia2は同一リージョンとして扱います」＋ europe/america 1.5倍。
- 選択肢（軽い順）:
  1. asia2 の余力活用: asia1 と asia2 は同一リージョン（遅延なし）。DB 負荷が下がったら asia1 の nginx から asia2 上にも Go アプリを置いて asia トラフィックを分散できる（ルーター経由の転送は維持）。
  2. **リージョンごとの PostgreSQL レプリカ**: europe1 / america1 にストリーミングレプリカを置き、読み取りをローカル化。「書き込み後の読み取り反映（リージョンをまたぐ場合も）」が必須のため、プライマリの `synchronous_standby_names`＋`synchronous_commit = remote_apply` で書き込み時に全レプリカ適用を待つ構成にする。読み取り（フィード20回/画像4回/…）が書き込み（投稿1・RealMoji5・コメント5）を大きく上回るため、書き込みに WAN 1往復を払う価値がある。
  3. リージョン別にデータを分割配置（各リージョンのユーザー・投稿をローカル DB に置き、クロスリージョンのフィードだけリモートを引く）: 効果は最大だが実装・整合リスクも最大。2 で足りなければ。
- 過去事例: reference 観点15（[12f] App1台・DB4台、[10q] テーブル単位分割）。本回は「JOIN を切る」のではなく「レイテンシドメインで切る」点が過去回と違う。
- リスク: 追試（再起動順序保証なし）でレプリカ構成が自動復旧すること。`isucon-register.service`・envcheck 対象ファイルに触れないこと。レプリケーション接続もルーター経由を維持（迂回禁止）。

### 施策11: initialize レスポンスの申告更新【効果: スコア外・必須 / 序盤】

- 根拠: 「エージェントで最適化する場合は、使用したものに合わせて各項目を書き換えてください」「`model` に複数のモデルを記録する場合は…カンマで区切ります」。得点・合否には使わないが申告義務がある。言語賞（Go＝ミラー賞）は「最後の負荷走行の `language` フィールド」で判定。
- 施策: [go/initialize.go:30](../go/initialize.go#L30) を実態に合わせて更新する（例: `agent: "claude-code"`, `harness: "claude-code"`, `model: "claude-fable-5"`。複数モデル併用ならカンマ区切り）。`language` は `go` のまま維持。

## 4. 壊してはいけない制約（チェックリスト）

- **クリティカルエラー6種**（即FAIL）: 初期ユーザーのログイン401 / フィードへの権限外・不存在投稿 / 権限外投稿の取得 / 権限外への RealMoji・コメント受理 / Memories・エクスポートの初期データ期待値不一致 / 削除5秒後の画像取得可。
- 画像署名: 形式（exp・sig パラメータ、base64url、HMAC-SHA256 反復1000回の値）と検証結果を変えない。不正署名・期限切れ・無効画像は 403。
- 即時反映: 削除画像の5秒以外に猶予なし。リージョンをまたいでも書き込み後の読み取りに反映。公開範囲・友達関係・ブロックは画像猶予の対象外。
- 外部仕様: URI / メソッド / ステータス / JSON・HTML 構造、静的ファイル内容、認証・閲覧制限・公開範囲・削除、初期データ、ブラウザからの利用。
- アカウント: 管理者 `admin` の変更・削除禁止。初期データユーザーの SecretKey でログイン可能なこと（secret_key_hash の保存方式を変えない）。
- インフラ: ルーター迂回禁止（サーバ間通信含む）・ルーターログイン禁止・リージョン/遅延/帯域の変更回避禁止。SG の 22/443/8080 変更禁止。インスタンスタイプ変更禁止。競技終了時に4台とも起動状態・単一スタック。
- 変更禁止ファイル: `isucon-register.service` 関連、`isuadmin` ユーザー関連、envcheck 一式（`/usr/local/bin/envcheck` ほか）。
- initialize: 変更したデータ構造・キャッシュ・複製先を含め全リージョンで初期状態へ戻す。初期データの履歴と画像を取得できる状態を保つ。`language` を空にしない（`lang` ではない）。
- 追試: 再起動後にベンチ中の書き込みデータが読めること（オンメモリのみの保持は不可）。最終スコアの75%を再現できる構成で終える（温まったキャッシュ前提のスコアで終えない）。
- 競技終了後（18:00以降）: アナウンスまで環境への接続・操作をしない。
- 最終スコアは「最後に行った負荷走行」。終了間際の攻めた変更は、最後に通る1回を確保してから。

## 5. 要確認事項（ポータルで質問する候補）

1. **削除5秒猶予の適用範囲**: 「投稿の削除」以外（RealMoji の削除・差し替え、プロフィール画像の削除、退会）で、その画像が取得できなくなるまでの猶予はあるか。即時か。
2. **IP BAN の可否**: 不正署名リクエストを送る IP（X-Client-IP）に対し、以降のリクエストへ 403 を返してよいか。初期実装の ip_bans 機構はそのために使ってよいか。
3. **署名付き URL の exp**: 「現在時刻から24時間」ちょうどである必要があるか。24時間以上（例: 分単位への切り上げ）でもよいか。
4. **ranked フィードのページング整合**: friends-of-friends フィードで、ページング中にスコアが変動した場合の期待挙動（スナップショット可か）。
